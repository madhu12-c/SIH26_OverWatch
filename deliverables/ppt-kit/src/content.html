2IDEA TITLE · PROPOSED SOLUTIONproblem understanding + novelty
Idea title

One Nation, One Material Code — match materials on specifications, not spelling

Detailed explanation of the proposed solution
  • Read every CPSE material description into typed specifications — size, grade, pressure class, standard — keeping the exact words each value came from.
  • Match on specifications; issue one National Material Code; keep every company's own code, mapped. Nothing is deleted.
  • Refuse safely: one mismatch on a veto field (grade, pressure class, size) and the merge is refused — with the reason.
How it addresses the problem
  • Finds the same item written differently, inside a company and across CPSEs: “Line Pipe 101.60 mm … 12.66 PPF” and “Line Pipe, 4″ … 12.66 PPF” are one pipe — the weight proves it.
  • Stops new duplicates: a creation gate checks every new request before a code is issued.
  • Gives each company a mapping file for its SAP team, and procurement a view of what CPSEs buy in common.
Innovation and uniqueness
  • Specifications, not spelling. Text matchers are 6–8% right at their best; ours made 0 wrong merges.
  • Engineering standards built in: ISO 15 bearings, ASME B36.10 pipe, IS 1367 = ISO 898-1, withdrawn ASTM grades mapped to F3125.
  • Every refusal explained: “if the grade matched, this pair would score 0.956.”
  • Catches a line that contradicts itself — a “6205” bearing written with a 6206's size.
  • Federated and governed: prices and vendors never leave a company raw; any company can dispute a link; every decision is sealed in an audit log.

Say — the problem (20 seconds). “India has 272 operating CPSEs. Each keeps its own material master. The same gate valve gets a different code and a different description in every company — so nobody can see that five companies buy the same item, and duplicates pile up in stores.”

Why descriptions are so messy — say it this way. “Several reasons: SAP's standard description field is still 40 characters, data came over from older systems, and above all there was never an enforced cataloguing standard — so every storekeeper invented their own shorthand.” Never blame SAP alone; a CPCL judge will know the real cause is the missing cataloguing policy.

The inversion (the line to remember). “Two records for one bearing share almost no words. Two records for different steel share almost all of them. Text matching scores the wrong pair higher. No threshold can fix an inverted order — so we changed what is measured.”

Why grade matters. “SS316 carries 2–3% molybdenum; SS304 has none. In chloride service the wrong one pits and leaks.”

3TECHNICAL APPROACHcomplexity + clarity
Technologies to be used
  • Python pipeline — normaliser, rule reader, standards tables (ISO 15, ASME B36.10), scorer, clustering
  • LLM (Gemini / Claude) — reads a description once per record, never per pair; rules run first, offline
  • Local embeddings — sentence-transformers, 384-dimension vectors; no internet needed
  • Scale: blocking with identity keys (skips 99.8% of pairs); PostgreSQL + pgvector at national scale
  • Portal: React + Tailwind, government style, role-based; runs offline; FastAPI service in the next phase
  • Trust: 292 automated tests · SHA-256 sealed audit log · UNSPSC classification
Methodology and process for implementation
  • Flow chart: architecture.png (full width) — eight stages, three lanes: read · match · registry
  • The AI reads; the rules decide. AI in two places: an LLM reads each record once, and embeddings find candidates. Every merge is decided by rules and can be explained. A statistical bound measures the error (< 0.35% at 95%); it does not limit it.
Working prototype (one screenshot)

screen-review-queue.png or screen-real-text.png

Say. “Three stages. First we read: every description becomes typed specifications, once, with the words each value came from. Then we match — with numbers only, no AI per pair, so it is cheap and every decision can be replayed. Safety fields veto a merge outright. Last, the registry: one national code, every company code kept, and a sealed log of who decided what.”

If asked “why not just use ChatGPT to match?” “An LLM per pair is millions of calls, costly, and not reproducible. We call it once per record to read, and let rules decide — so a judge, an auditor or a CPSE can check every merge.”

Be accurate about the stack: the pipeline, portal, tests and audit log are built and running; FastAPI, PostgreSQL/pgvector and Docker are the decided production stack, not yet built. Say “next phase” for those.

4FEASIBILITY AND VIABILITYfeasibility + practicability
Analysis of the feasibility of the idea
  • Working prototype, measured — runs end to end on a laptop, offline. Numbers strip: numbers.png
  • 15,000 records written the way NTPC, Oil India and SAP write: 860 merged automatically, 0 wrong (below 0.35% at 95% confidence); 0 of 104,994 near-miss traps merged; 82% of duplicates found with a reviewer.
  • Beats text matching on the same pairs (chart text-vs-specs.png): fuzzy, TF-IDF and embeddings are 6–8% right at their best; no text threshold reaches zero wrong.
  • Real tender text — 252 held-back Oil India and NTPC lines: item type read right 98%, 0 wrong merges, 83% of true duplicate pairs found with a reviewer.
Potential challenges and risks → strategies for overcoming them
ChallengeStrategy
No CPSE will share prices or vendor listsFederated: only price bands and vendor hashes cross the boundary; a benchmark is hidden below 3 companies. Phase 1 — duplicates inside one company — needs no sharing at all.
A wrong merge can put the wrong valve in a lineVeto fields; a safety field unstated on one side goes to a person; self-check; a measured error bound; people decide every uncertain pair.
Descriptions are cryptic and inconsistentNormaliser + engineering standards + evidence for every value; tested on real tender text, not only on our own data.
Millions of recordsBlocking skips 99.8% of pairs; the LLM runs once per record, never per pair.
Reviewers do the work, others get the benefitOnly genuinely uncertain pairs reach a person; one record with its top three candidates; keyboard only; the gate stops new mess.
Our generated data could flatter usA real hold-out, labelled separately by two people, is reported beside it — never blended.

Say — the honest line (it wins trust). “Our 15,000-record numbers measure how well we undo noise we generated ourselves. That is why the real tender test sits beside them. Its weak point is real: only about one in five pairs we send a reviewer is a true duplicate, because a short line fits several items. So the reviewer sees one record with its best three candidates — the right one is in the top three about four times in five.”

5IMPACT AND BENEFITSscale of impact + sustainability
Potential impact on the target audience
  • Cataloguers / reviewers — decide only the genuinely uncertain pairs, with the evidence on one screen.
  • Storekeepers — a new request is checked before a code is issued; the gate says what an item is not.
  • Procurement officers — see what several CPSEs buy in common: joint tenders, better prices.
  • CPSE SAP teams — a ready mapping file: company code → national code.
  • MoPNG / national registry — one national view, savings and a governance trail.
Benefits of the solution
  • Economic: published cases report ~5–7% lower inventory cost after de-duplication, and ~10% potential MRO savings at an oil & gas company. On our demo data: ₹2.31 cr upper / ₹0.92 cr realistic saving on ₹22.6 cr of spend.
  • Safety: 13,127 unsafe merges refused that were one field from happening — SS304 kept apart from SS316.
  • Operational: duplicates stopped at creation; every merge explained, reversible, and sealed in an audit log.
  • National: an Indian registry on BIS / ISO standards; company data stays with the company.
  • Environmental: less duplicate stock means less dead inventory later written off and scrapped.

JUDGE QUESTIONS — short answersfor Meghna (story) and Madhu / Yash (technical)
QuestionAnswer
Why not just buy SAP MDG or Informatica?They are built for one enterprise and need all data in one place. No CPSE will hand over its prices and vendor list. Ours works federated — only bands and hashes cross — and it is an Indian registry for national procurement data.
Isn't this just string matching?The opposite. Text matching scores SS316 vs SS304 at 0.989 and would merge them. We match on specifications and veto on grade — and on the same 15,000 records the text methods are 6–8% right while ours made 0 wrong merges.
Your data is synthetic — why believe it?Fair — it measures how well we undo noise we generated. So we test on 252 real NTPC and Oil India lines held back while building: 0 wrong merges, item type 98%. We report both, never blended.
What if the AI hallucinates a grade?The LLM only reads — it never decides a merge. The rule reader runs first and every value it takes keeps the words it came from; a record that contradicts itself is held for a person; the rules decide. Next phase: the LLM must quote its words, and a value whose quote is not in the line is dropped.
Who approves a merge between two companies?The national registrar links codes; any affected company can dispute at any time and the link returns to review; only the owning company can retire its own code. Every step is in a sealed audit log.
How does it scale to millions?One LLM call per record, stored; pairwise scoring is arithmetic. Blocking skips 99.8% of pairs. At national scale: PostgreSQL + pgvector.
Is 150# the same as 150 psi?No — 150# is an ASME B16.5 pressure class; a Class 150 carbon-steel flange is rated around 285 psig at ambient and less when hot. That is why pressure class is a veto field.
What is your weakest number?Review precision: about one in five pairs sent to a reviewer is a true duplicate, because a short line fits several items. So the reviewer sees one record with its three best candidates — the right one is there about four times in five.
Will CPSEs actually change their codes?They don't have to. The national code sits above their codes and links them; every original code stays in use. Phase 1 cleans duplicates inside one company with no data sharing at all.

Do not say

  • “100% accurate” or “100% precision” — say “0 wrong out of 860” and “below 0.35% at 95% confidence”.
  • “Production-ready”, “live SAP integration”, “secure”, “encrypted” — say prototype, SAP-shaped export file, reduces data exposure.
  • “Material master” about the real data — it is tender text from two CPSEs.
  • “Descriptions are cryptic because SAP caps them at 40 characters” — give the several-reasons version on slide 2.
  • Any synthetic number without the real one beside it; any saving as a promise rather than “published case studies report”.
  • That named vendors supply CPCL — that is not public information.
